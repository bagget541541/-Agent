# Mode C 公众号文章解析：问题复盘与改进规范

> 版本：v1.0 ｜ 日期：2026-08-01
> 来源：2026-08-01 对 8 篇银行公众号文章执行"抓取→提取→OCR→整理"全链路后的复盘

---

## 一、背景

Mode C 负责**公众号文章解析**：输入微信文章 URL，输出结构化资讯（分类、活动内容、金额、有效期、适用人群等），供下游 Mode D 合并点评、生成周报。

2026-08-01 的一次真实执行暴露了链路中的系统性缺陷：8 篇输入中有 **3 篇输出内容与原文完全不符**、1 篇缺失近半、2 篇同银行文章互相串稿，且来源声明与事实不符。

本规范旨在固化问题认知与改进方案，作为 Mode C 解析节点的 Prompt / 工作流 / 质量门禁设计依据。

---

## 二、问题诊断（按严重程度排序）

### P0-1 抓不到内容时"编造"而非"如实失败"（最危险）

- **现象**：原文档声明"因微信公众号文章受 robots.txt 限制无法直接抓取，通过多渠道搜索交叉验证提取"——与事实不符，8 篇页面全部可直连抓取。
- **后果**：长安银行（实为文旅秒杀）写成产品介绍、北京农商（实为青少年夏令营）写成系统升级公告、中国银行（实为留学缴费补贴）写成月月返活动。输出看似完整，实则全是幻觉。
- **根因**：解析节点在拿不到正文时，用"该银行通常有什么活动"的常识脑补填充，而不是报告"内容不可得"。

### P0-2 正文图片化，纯文本提取必然失败

- **现象**：银行推文正文几乎 100% 为设计图片，页面可提取的可见文字仅有"编辑：xxx""以上内容为广告""点击阅读原文"等碎片。
- **后果**：无 OCR 环节时，输出中的具体金额、日期、名额全部无源可依。
- **根因**：链路缺少 OCR 环节，且未对"正文是否可提取"做检测。

### P1-3 抓取技术细节缺失

- `web_fetch` 对 3MB+ 微信页面直接截断（响应超 2MB 提前中断），须改用 `curl + UA`。
- 图片懒加载：必须取 `data-src` 而非 `src`。
- 正文区间需从 `id="js_content"` 截取到 `js_tags`/`rich_media_tool`，否则混入页脚 JS。
- 每页约 3MB，一次全量处理易超时，需分批。

### P1-4 无溯源、无置信度标注

- 所有来源标"（推测）"，金额/日期/名额均无出处。
- 未保留 URL、公众号名、发布时间等元数据，下游无法回溯核对。

### P1-5 同一银行多篇文章串稿

- 兴业两篇（全攻略 vs 兴运月月抽）内容互串，"满18减2-88"被同时写进两篇，抽奖篇出现原文不存在的"携程满减"。
- 根因：以银行名分组而非以 URL 为主键隔离。

## 三、改进方案

### 3.1 抓取策略分层

```
L1 直抓：curl/UA 直连 → 解析 og:title、公众号名、发布时间、js_content 正文文本
L2 OCR ：正文图片化时，提取 data-src 图片 → 本地 OCR（rapidocr_onnxruntime）
L3 兜底：L1/L2 均无效 → 输出明确标记"未获取到内容"，禁止用常识填充
```

**硬性门禁**：解析结果与 og:title 主题相似度低于阈值即丢弃或标记人工复核。本次长安/北京农商/中行三篇标题与内容完全无关，此类偏差可用标题-正文关键词相关性自动拦截。

### 3.2 输出三段式结构（带溯源）

每篇文章固定输出：

| 段 | 内容 |
|----|------|
| 元数据 | URL、公众号名、og:title、发布时间（微信页含 publish_time） |
| 正文文本层 | 页面可提取的文本（若有） |
| OCR 文本层 | 图片转写文本，保留图片序号便于回溯（如"OCR-图03"） |

下游 Mode D 需要"属性/类别/优先级/活动内容"结构，解析阶段即应为金额、门槛、名额、有效期等字段打上**来源标签**，而非让下游模型猜测。

### 3.3 事实标注规范

- 每个数字/日期/名额必须能追溯到 OCR 原文或页面文本；
- 无法核实的统一标注"原文未识别/未核实"，**宁缺毋滥，绝不编一个错数**；
- 删除"多渠道搜索交叉验证"这类无出处措辞。

### 3.4 OCR 工程化

- **断点续跑**：按图片记录进度，失败不重扫（本次 142 张分 4 批完成）；
- **按篇分组、超时控制**：每批 30–40 张、单批 ≤280s；
- **预处理提升识别率**：图片放大 2 倍、灰度化后再识别；低于置信度阈值的片段直接标"未识别"；
- **性能**：只 OCR 正文区图片（跳过二维码/头像/尾图）；批量采集时可并发 2–4 路或 GPU 加速（paddleocr）。

### 3.5 防混稿

- 以 **URL 为主键**去重与分组，同一银行多篇严格按 URL 隔离；
- 输出保留 URL 列，供下游合并点评时溯源。

## 四、Mode C 解析节点 Prompt 要点（建议纳入）

1. **先抓后写**：必须先完成抓取/OCR 再生成整理内容；内容不可得时如实报告。
2. **禁止编造**：不得用常识、推测或"通常情况"填充原文没有的信息。
3. **来源标注**：每个关键事实（金额、门槛、名额、有效期）附 OCR 图号或页面文本出处。
4. **未识别即标注**：识别不清的小字（价格、日期）标"（原文图片未识别）"，不猜测。
5. **按 URL 隔离**：同一银行多篇文章各自独立整理，禁止互相引用。
6. **元数据完备**：输出含 URL、公众号名、标题、发布时间。

## 五、质量门禁清单（解析后校验）

- [ ] 输出内容与 og:title 主题一致（关键词相关性校验）
- [ ] 每个数字/日期可溯源（OCR 图号或页面文本）
- [ ] 无"（推测）""交叉验证"等无出处措辞
- [ ] 正文图片化文章已过 OCR 环节
- [ ] 同一银行多篇按 URL 区分，无串稿
- [ ] 抓取失败/OCR 无效的文章已标注"未获取到内容"，未填充虚构内容

## 七、审核结论与补充要求

### 7.1 总体审核结论

本规范的问题判断和总体方向基本正确，尤其是“不可得则失败、图片正文必须 OCR、按 URL 隔离、事实带来源”等原则。但当前版本更接近改进原则清单，尚不足以直接作为开发完成标准。

实施前必须补齐数据契约、失败状态、阈值定义、测试样本和可执行验收指标。以下要求与前文具有同等约束力。

### 7.2 标题-正文一致性门禁

标题-正文相似度只能用于风险筛查，不得在低分时直接丢弃文章。低分结果统一进入人工复核队列，并保留原始抓取内容和 OCR 结果。

必须明确以下实现参数：

- 分词和关键词归一化规则；
- OCR 错别字、数字和银行名称的容错规则；
- 标题与正文的比较文本范围；
- 相似度算法、阈值和阈值校准样本；
- 多主题文章的标题匹配规则；
- 缺少标题、正文或 OCR 结果时的处理方式。

不得仅以简单关键词数量作为唯一判定依据。标题营销化、正文 OCR 噪声较大或文章包含多个主题时，应降低自动拦截强度。

### 7.3 数据契约与字段级溯源

“来源标签”必须落实为结构化字段，不能只在最终 Markdown 中添加自然语言说明。建议关键事实统一采用以下格式：

```json
{
  "value": "满18元",
  "field": "threshold",
  "source_type": "ocr",
  "image_id": "OCR-图03",
  "quote": "单笔消费满18元",
  "confidence": 0.94
}
```

每个金额、日期、门槛、名额、比例、次数和适用条件必须关联至少一个 `evidence` 记录。`source_type` 至少支持 `page_text`、`ocr` 和 `manual`，并明确人工修正时必须保留修正原因。

建议在文章级数据中增加以下字段：

```text
extraction_status: SUCCESS | PARTIAL | FETCH_FAILED | OCR_FAILED | NEEDS_REVIEW
fetch_status
ocr_status
content_text_ratio
image_count
evidence_coverage
review_reasons
```

当前项目已有 `ArticleEnvelope` 和 `CreditCardItem.evidence` 字段，实施时应扩展现有契约，避免另建一套互不兼容的输出格式。

### 7.4 失败状态和下游隔离

“未获取到内容”“原文未识别/未核实”必须对应明确的机器可读状态，不得只依赖展示文本。

- `FETCH_FAILED`：页面未成功获取，不得生成活动事实；
- `OCR_FAILED`：页面成功获取但图片文字无法识别，不得猜测关键字段；
- `PARTIAL`：仅部分内容可核实，所有缺失字段必须单独标记；
- `NEEDS_REVIEW`：自动门禁发现疑似串稿、主题不一致或证据不足；
- 只有 `SUCCESS` 或经过人工确认的 `PARTIAL` 才能进入下游点评流程。

失败文章可以保留在批次结果中，但必须禁止下游模型把失败状态解释为“没有优惠”或用银行常识补全内容。

### 7.5 正文图片化检测

“正文图片化”必须有可执行的检测标准。至少记录并判断：

- 正文有效文本字符数；
- 正文图片数量及图片占比；
- 页面有效文本占正文总内容的比例；
- 是否仅包含页脚、广告声明和导航噪声；
- 是否存在 `data-src`、`data-original` 等懒加载图片地址。

建议将检测结果写入文章元数据，并根据阈值决定是否进入 OCR，而不是仅由解析模型自行判断。

### 7.6 抓取规则的健壮性

`js_content`、`js_tags` 和 `rich_media_tool` 只能作为当前页面结构的优先选择器，必须提供备用选择器和失败诊断信息。

直抓实现至少应明确：

- User-Agent、Accept-Language 和 Referer 策略；
- 连接超时、读取超时、重试次数和退避策略；
- HTTP 状态码、重定向和字符编码处理；
- 最大响应大小和内容类型校验；
- 原始 HTML、解析版本和抓取时间的保存方式；
- 页面结构变化时的 `FETCH_FAILED` 或 `NEEDS_REVIEW` 处理。

对用户输入 URL 下载页面和图片时，还应限制协议、响应大小和重定向目标，避免下载非预期资源。

### 7.7 URL 规范化与幂等

“按 URL 为主键”必须补充 URL 规范化规则。建议同时保留：

- `source_url`：用户输入的原始 URL；
- `canonical_url`：去除无关参数并规范化后的 URL；
- `article_id`：基于 `canonical_url` 生成的稳定 ID；
- `url_hash`：用于缓存、去重和断点续跑。

必须明确查询参数、短链接、重复抓取、同一文章不同入口 URL 和 URL 失效时的处理方式。同一银行的不同文章不得仅通过银行名称分组或共享上下文。

### 7.8 OCR 工程化补充

当前项目依赖中尚未固定 OCR 引擎，接入 `rapidocr_onnxruntime` 前必须补充依赖版本、模型来源、模型缓存目录、CPU/Windows 兼容性和首次初始化策略。

OCR 工程化要求还应包括：

- 单图片超时、失败重试和失败后跳过策略；
- 断点状态持久化，确保进程中断后可幂等恢复；
- 图片哈希去重，避免同图重复识别；
- 词级、行级、图片级和字段级置信度的聚合规则；
- 放大、灰度化等预处理的启用条件和效果验证；
- 并发数、批大小和超时均为可配置项，不得固定写死为 30–40 张或 280 秒；
- 二维码、头像和尾图的可执行过滤规则，并支持人工强制纳入。

“放大 2 倍、灰度化”不应默认视为一定提升识别率，必须通过回归样本验证后启用。

### 7.9 质量门禁的量化验收

第五章清单必须同时提供自动检查和人工复核入口。建议采用以下最低验收标准：

- 关键字段证据覆盖率为 100%；
- 无来源金额、日期、名额和门槛数量为 0；
- URL 串稿数量为 0；
- 抓取或 OCR 失败文章不得生成无依据的结构化活动事实；
- 标题-正文一致性低分文章全部进入人工复核；
- 8 篇事故回归样本中，主题错配数量为 0；
- 所有 `DONE` 文章均保留 URL、公众号名、标题和发布时间，无法获取时明确标记缺失原因。

### 7.10 回归样本和复盘证据

本次 8 篇文章应固化为回归测试集，至少保存文章 URL、原始 HTML、正文图片、OCR 输出、期望主题和关键事实证据。对“长安银行、北京农商银行、中国银行”三篇主题错配样本以及两篇兴业银行串稿样本，必须提供输入输出对照。

第 12、22、23、46 行记录的事故和第 83 行提到的“142 张图片分 4 批完成”应有对应的抓取日志、批处理记录或结果文件，确保后续能够复现，而不是只保留文字描述。

### 7.11 建议实施顺序

1. 先确定 `ArticleEnvelope`、`ContentBlock`、字段级 `Evidence` 和 `extraction_status` 数据契约；
2. 实现直抓、图片提取、OCR、URL 规范化和按 URL 的幂等隔离；
3. 用本次 8 篇文章建立固定回归样本，保存 HTML、图片、OCR 结果和期望标签；
4. 实现失败状态隔离和证据覆盖率检查；
5. 最后上线标题一致性门禁和质量评分，低分结果进入人工复核，不直接丢弃。

### 7.12 审核后的发布条件

在完成 7.2 至 7.10 的补充定义并通过 8 篇回归样本验证前，本规范状态为“可作为设计草案，不可作为开发完成验收标准”。
