# Mode C 公众号文章解析代码审查报告

> 审查日期：2026-08-01
> 审查范围：本次新增/修改的 Mode C 提取、抓取、OCR、门禁、标题评分、schema 与回归脚本。
> 审查方式：静态代码审查；未执行可能改写缓存或样本的命令。

---

## 审查结论

发现 4 项需要修复的问题。其中前两项会破坏“关键事实必须溯源”和“失败状态不得被下游绕过”两条 P0 约束，建议修复后再将 Mode C 接入 Mode D。

## Findings

### P0-1 证据覆盖率按字段名放行，错误事实可被视为已溯源

- 位置：`common/extraction_gate.py:130-132`
- 问题：只要某字段存在任意一条 evidence，代码即将该字段扫描出的所有事实标记为已覆盖，而不校验具体的金额、日期、名额或门槛是否与 evidence 的 `value` / `quote` 对应。
- 影响：例如 evidence 中只有“满18元”，正文同时有“满18元、满5000元”，`threshold` 字段会使两项均通过；`evidence_coverage` 可错误达到 100%，`SUCCESS` 状态和下游放行都会建立在错误结果上。
- 修复：删除字段级兜底放行逻辑；逐个 fact 与同字段 evidence 做归一化后的精确/数字 token 匹配，匹配失败必须保留在 `uncovered`。同时先调用 `validate_field_evidence`，非法 evidence 不得参与覆盖计算。

### P0-2 未确认的 `PARTIAL` / `NEEDS_REVIEW` 仍向下游暴露活动事实与结构化内容

- 位置：`common/extraction_gate.py:194-208`
- 问题：`build_downstream_view()` 虽计算 `safe = is_downstream_safe(...)`，但仅对 `FETCH_FAILED` 和 `OCR_FAILED` 清空 `activity_facts`、`structured`。未人工确认的 `PARTIAL` 与所有 `NEEDS_REVIEW` 仍返回 `content_blocks` 和 `structured`。
- 影响：下游若忽略 `downstream_safe`，可直接消费待复核或证据不足文章的事实，违反“只有 SUCCESS 或经人工确认的 PARTIAL 才允许进入下游点评”的契约；标题低分导致的串稿风险无法真正隔离。
- 修复：以 `safe` 为唯一放行条件。`safe == false` 时统一返回空 `activity_facts` / `structured`，并保留仅供人工复核的原始内容字段；或者将下游 API 拆分为安全视图和审核视图，杜绝调用方拿到未放行字段。

### P1-3 `check_batch_gate()` 对生成器二次迭代，报告 `total` 会错误为 0

- 位置：`common/extraction_gate.py:242`、`common/extraction_gate.py:318`
- 问题：函数先遍历 `articles` 做检查，再用 `sum(1 for _ in articles)` 统计总数。传入 generator、iterator 或数据库流时，第二次迭代已经耗尽。
- 影响：验收报告的总数与实际检查数量不一致，可能导致“8 篇样本全部审完”的批量验收被错误报告为 0 篇。
- 修复：入口先执行 `article_list = list(articles)`，后续统一遍历该列表，并以 `len(article_list)` 作为 `total`。

### P1-4 OCR 超时不会停止引擎调用，可能积压后台线程并让后续任务失去超时边界

- 位置：`common/ocr.py:186-196`
- 问题：每次 OCR 会新建 daemon thread，超时后直接返回；实际 RapidOCR 调用仍在后台运行，并继续持有单引擎锁。后续任务会在锁上等待，调用者却已经将当前图片标记为失败。
- 影响：连续卡死图片会积压无法取消的后台线程；当 `max_workers > 1` 时，批处理表面上超时返回，实际引擎队列继续执行，单图/批次超时预算不成立，也可能在进程退出时丢失进度。
- 修复：将 OCR 放到可终止的独立进程或长期 worker 进程中，超时后重建 worker；若暂不支持硬终止，至少禁止将该机制表述为超时控制，并在超时后停止提交同一引擎的新任务、等待或重建引擎。

## 风险与建议

- `common/ocr.py:101-108`：`_get_engine()` 在 `max_workers > 1` 时没有初始化锁，多个 worker 可同时看到 `_engine is None` 并重复初始化 RapidOCR。应以独立初始化锁保护创建过程；现有 `_lock` 只保护实际识别调用。
- `common/ocr.py:82-97`：单次 `ocr_images()` 内 `_mark()` 由主线程调用，基本安全；但同一 `OCRModule` 被多个调用方并发使用时，共享 `progress` 与固定的 `.tmp` 文件并不安全。需要声明实例非线程安全，或给进度读写加锁并采用唯一临时文件名。
- `common/schema.py:323-333`：新字段均使用 `dict.get(..., default)`，对旧 JSON 的字段缺失保持向后兼容；本次未发现旧数据 `from_dict` 的破坏性变更。

## 已核对的正向项

- 标题一致性已采用按分隔符切块、整块子串/块内词元/数字归一化命中，避免了初版窗口切词碎片导致的误判。
- `manual` 类型证据要求填写 `reason`，`ocr` 类型证据要求 `image_id`，基本契约具备。
- OCR 单引擎调用处设有锁，默认并发为 1；问题在于配置提升并发时的初始化、超时和跨调用进度安全，而非默认串行路径。

## 建议复验

修复后应增加以下回归断言：

1. 同字段的两个不同金额/日期，只有对应 evidence 的事实通过，另一项必须进入 `uncovered`；
2. `PARTIAL`（未确认）和 `NEEDS_REVIEW` 的安全视图中，`activity_facts` 与 `structured` 均为空；
3. 用 generator 传入 `check_batch_gate()`，`total` 与实际文章数量一致；
4. 模拟 OCR 永久阻塞，验证超时后不会继续占用引擎或导致后续批次无限等待；
5. `max_workers=2` 并行首启，断言 RapidOCR 仅初始化一次；
6. 旧版 batch JSON 经过 `CreditCardBatch.load_json()` 与 `save_json()` 后可正常序列化，新增字段使用默认值。
